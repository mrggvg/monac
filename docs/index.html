Is this the right simulator? Mona targets the 16-bit Assembly Simulator used in Sistemi I (Systems I) at UP FAMNIT, the University of Primorska in Koper — the one served from Moodle at e.famnit.upr.si. You are in the right place if your machine has registers A, B, C and D, 4 KB of RAM, a text display at 0x1000, a graphics card on the I/O ports, and no MOD instruction.

The simulator itself is published here, so you can paste assembly in and run it without going through Moodle, and its instruction set reference is next to it. Both are copies of the course's own; see where they come from.

01 Getting started

Mona is written in a text editor and compiled on your own machine; what comes out is ordinary assembly for the 16-bit Assembly Simulator, which you paste in and run. There is nothing to install on the simulator's side.

What you need

toolwhy
A JDK, version 21 or newerthe compiler is a Java program. It must be a JDK, not just a JRE: javac -version should answer.
Maven 3.9 or newerto build the compiler from source, once.
The simulatoropen it here, or use the course's copy — they are the same.
Node.js (optional)only for running the compiler's own end-to-end tests.

Build the compiler, once

git clone https://github.com/mrggvg/monac.git
cd monac
mvn package                     # builds target/monac.jar
java -jar target/monac.jar --help

Typing java -jar …/monac.jar gets old quickly, so give it a name. Everything else on this page writes plain monac.

alias monac='java -jar ~/monac/target/monac.jar'
function monac { java -jar $HOME\monac\target\monac.jar @args }
error: release version 21 not supported? Maven is running on a Java without a compiler in it. The build tries to find a javac on the PATH by itself; if there is none, point JAVA_HOME at a real JDK and run mvn package again. building.md has the details.

Your first program, start to finish

  1. Write it. Save this as hello.mona: 
    byte* const SCREEN = 4096;       // the text display, 32 characters at 0x1000

word main() {
    const byte* text = "HELLO, MONA";
    word i = 0;
    while (text[i] != 0) {
        SCREEN[i] = text[i];
        i++;
    }
    return i;                        // 11, left in register A
}
  2. Compile it. monac hello.mona writes hello.asm next to it. Add --stats to see what it costs: 
    $ monac hello.mona --stats
monac: 30 instructions, 102 bytes of 4096
monac: stack at most 4 bytes, 3994 bytes free
  3. Load it. Open hello.asm, copy all of it, paste it into the simulator's editor, and press Assemble.
  4. Run it. Pick a speed first — the default of 4 Hz is for stepping through code one instruction at a time, and a program of any size wants 10 kHz or more — then press Run. When main returns the machine halts, A holds 11, and the text display reads HELLO, MONA.

That is the whole loop: edit, compile, paste, assemble, run. When something surprises you, the flags in the next section show every stage in between.

02 Hello, machine

Every program is one file with a main. There is no #include, no linker and no library — one file becomes one image, and that image holds the code, the data, the heap and the stack inside 4 KB. Whatever main returns is left in register A when the machine halts.

// Euclid, in the language's whole vocabulary: a loop, a modulo, two locals.
word gcd(word a, word b) {
    while (b != 0) {
        word t = b;
        b = a % b;
        a = t;
    }
    return a;
}

word main() {
    return gcd(1071, 462);      // 21
}
monac gcd.mona -o gcd.asm       // then paste gcd.asm into the simulator

Four numeric types, plus pointers, arrays and structs. That is the whole type system.

Writing numbers

Every integer constant C has, meaning the same thing it means in C. A leading 0 is octal, so 010 is eight and 09 is an error.

writtenvaluewhat it is
4242decimal
0x1F, 0X1f31hexadecimal
01715octal — a leading zero
0b1011, 0B101111binary
1'000, 0b1010'10101000, 170with C23 digit separators, which mean nothing
10u, 0xFFul, 7LLU10, 255, 7with C's suffixes, accepted and ignored: every integer here is 16 bits
'A', '\101', '\x41'65a character, an octal byte, a hexadecimal byte
"hi"—a byte* to a zero-terminated copy in the image

The escapes are C's whole set: \n, \t, \r, \b, \a, \f, \v, \\, \', \", \?, an octal byte of one to three digits, and \x with any number of hexadecimal digits. Anything above 255 is an error, and so is a literal above 65535.

Arithmetic is always 16-bit

A byte is a storage size. It widens to 16 bits to be computed with and truncates back on assignment, and the compiler warns when the truncation loses something.

byte b = 250;
b += 10;            // 4: a compound assignment narrows, as in C, and says nothing
byte c = 260;       // warns: 260 does not fit in a byte, and becomes 4
word w = b + 100;   // but the addition itself is 16-bit: 104

Signedness lives in the type, not the bits

The same sixteen bits mean different things depending on how you declared them — the type is what picks the instruction, since the machine has no sign flag to consult.

sword s = 0 - 7;
s / 2               // -3: division truncates toward zero
s % 2               // -1: the remainder takes the dividend's sign
s >> 1              // -4: an arithmetic shift, so the sign survives
s < 0               // true

word u = 65529;     // the same sixteen bits as -7
u < 0               // false: nothing unsigned is below zero
u > 1000            // true

Mixing the two families in one operator warns and treats the result as signed. Keep an expression to one family.

sizeof

sizeof(word)         // 2
sizeof(byte)         // 1
sizeof(word*)        // 2 -- every pointer is a word
sizeof(struct Node)  // the sum of its members, packed
sizeof(someArray)    // the whole array, not one element
sizeof(*p)           // the size of what p points at (p is not evaluated)

04 Declarations

A declaration is a statement, so it goes anywhere one does and is in scope to the end of its block. The initializer is optional.

word counter = 0;
word* cursor;                   // no initializer: uninitialized
byte flag = 1;
struct Point origin;            // aggregates declare fine without one
A local with no initializer holds whatever was in its frame slot. There is no zeroing pass — it would cost instructions on every call. A global with no initializer is zero, and that is not a promise the compiler keeps but one the machine does: RAM arrives cleared, which is also what the allocators rely on.

A global's initializer must fold to a constant, because there is nowhere to run code before main:

word size = 2 * 21;             // fine, folded to 42
word half = size / 2;           // error: must be a constant expression

Top-level items — functions, globals and structs — are in scope throughout the file whatever the order, so nothing needs declaring ahead of its use. A C prototype is still accepted, and checked against the definition.

const, enum and static

const word COLUMNS = 16;        // read-only, and a constant: it can size an array
byte row[COLUMNS];

enum Direction { UP, RIGHT, DOWN, LEFT };   // words with names: 0 to 3

word nextId() {
    static word issued = 0;     // one copy, kept between calls
    return ++issued;
}

word draw() {
    const byte* name = "mona";  // the bytes are read-only; name itself may move
    byte* const cursor = row;   // cursor may not move; *cursor may be written
    enum Direction facing = RIGHT;
    ...
}

const goes wherever C allows it and changes no code: it is a promise the compiler checks, down to writes through a pointer to const. A const scalar with a constant initializer is itself a constant, which C allows only from C23's constexpr. Enumerators have no storage, so they size arrays and label cases too. A static local is a global only its block can name, initialized once, in the image.

05 Expressions

C's operators at C's precedence, loosest first — including C's much-regretted placement of the bitwise operators below the comparisons.

2= += -= *= /= %= &= |= ^= <<= >>=right associative
3?:right associative; only the chosen arm runs
4||short-circuits
5&&short-circuits
6–8|   ^   &one level each, in that order
9== !=
10< <= > >=
11<< >>
12+ -
13* / %
14unary - + ! ~ & * ++ --   (type)   sizeofright associative
15a[i]   f(…)   s.f   p->f   x++   x--

0 && boom()         // boom() is not called: && short-circuits

All eleven compound assignments work, and so does the rest of C's expression syntax. Postfix ++ yields the old value and prefix the new, and a pointer steps by the size of what it points at. A cast narrows or reinterprets. ?: evaluates only the arm it picks, and the comma operator binds loosest of all.

k++                     // the old value; k is one higher afterwards
p++                     // a word* moves two bytes, a struct pointer its size
(byte)300               // 44: the end of & 255 as the low-byte idiom
(sword)65535            // -1: the same bits, read as signed
p != 0 ? p->x : 0       // never dereferences a null p
n < 5 ? 1 : n < 10 ? 2 : 3
for (i = 0, j = 9; i < j; i++, j--) { }
a = 1, 2                // assigns 1: the comma binds loosest

06 Control flow

if (a < b) {
    ...
} else if (a < c) {             // just an else whose statement is another if
    ...
} else {
    ...
}

while (count < 3) count += 1;   // braces optional around one statement
while (1) { ... }               // the endless-loop idiom

for (word i = 0; i < 5; i += 1) { ... }
for (; i < 5; i += 1) { }       // any of the three parts may be empty
for (word i = 0; ; i += 1) { }  // an empty condition means true

break;                          // leaves the nearest loop or switch
continue;                       // next iteration of the nearest loop

do {
    m = m * 2;
} while (m < 100);              // the body runs before the first test

A switch falls through exactly as C's does, which is a feature here rather than an accident — the arms hold statements, not blocks.

switch (n) {
    case 1: hits += 1;          // no break, so it falls into case 2
    case 2: hits += 10;
            break;
    case 3:
    case 4: hits += 100;        // several labels, one arm
            break;
    default: hits = 0;          // optional; a switch matching nothing does nothing
}

Case labels must fold to a constant — a character literal is one. The switched value need not.

for (word i = 0; i < 10; i++) {
    for (word j = 0; j < 10; j++) {
        if (grid[i][j] == target) goto found;   // out of both loops at once
    }
}
return 0;
found:
return 1;

goto stays within its function, may leave blocks but not enter them, and may not jump forward past a declaration.

07 Functions

word twice(word n) {
    return n + n;
}

void store(word* into, word value) {
    *into = value;
    return;                     // optional in a void function
}

word main() {
    return definedLater(6);     // order in the file does not matter
}

word definedLater(word n) {
    return n * n;
}

A C prototype is accepted all the same, and checked: every declaration of a function must agree with every other, before or after the definition. Parameter names are optional in one, (void) means no parameters, and calling a prototype that is never defined is an error at the call — where C would have waited for the linker.

word isOdd(word);               // no parameter name needed
void reset(void);

word isEven(word n) { return n == 0 ? 1 : isOdd(n - 1); }
word isOdd(word n)  { return n == 0 ? 0 : isEven(n - 1); }

Recursion works, mutual recursion included. The compiler computes the stack requirement from the call graph where it can; a cyclic call graph has no such number, so a recursive program instead gets a run-time guard that prints STACK OVERFLOW on the text display and halts — rather than quietly growing down into its own code.

word factorial(word n) {
    if (n <= 1) return 1;
    return n * factorial(n - 1);
}

The first argument travels in a register and the rest on the stack, which matters only because it makes a one-argument function meaningfully cheaper than a four-argument one.

Function pointers

word (*op)(word, word) = add;               // a function's name is its address
op = &mul;                                  // and so is &name
op(6, 7)                                    // 42, through CALL [A]

word (*ops[2])(word, word) = {add, mul};    // a table of them, in the image
struct Button { word id; void (*press)(void); };
__setisr(onKey);                            // what an interrupt handler always was

A pointer takes only a function of its own signature, or 0. The compiler cannot know which function a pointer holds, but it knows which it could — only one whose address was taken somewhere — so an indirect call counts as reaching every such function. The stack bound stays a number, and a cycle through a pointer is guarded like any other recursion.

08 Structs & pointers

Structs are declared at file scope, and struct is written at every use, as in C89. They are packed: no padding anywhere, so a byte followed by a word puts that word at an odd offset. The machine has no alignment requirement to satisfy.

struct Point { word x; word y; };
struct Point origin = {3, 4};           // a list, in member order
struct Mixed { byte flag; word value; sword delta; };   // sizeof is 5, not 6

struct Node {
    word key;
    struct Node* next;          // itself, through a pointer
};

struct A { word k; struct B* b; };      // and B is not even declared yet:
struct B { word j; struct A* a; };      // the layout pass runs to a fixpoint

A struct can be assigned — it copies every byte — but it cannot be passed to or returned from a function by value. The compiler says so, and tells you to pass a pointer.

struct Point a;
struct Point b;
b = a;                          // fine: a full copy, not an alias
a.x = 9;                        // b.x is still what it was

struct Point* p = &a;
p->y = 4;                       // p->f is (*p).f

Arrays

word table[4];                  // at file scope: zeroes
word primes[5] = {2, 3, 5, 7, 11};
word counted[] = {10, 20, 30};  // three: the list counts it
byte name[] = "mona";           // five bytes, terminator included
const byte* names[] = {"red", "green", "blue"};
word grid[3][4];                // three rows of four: grid[2][3]
word identity[2][2] = {{1, 0}, {0, 1}};

word total(word* values, word count) {      // an array parameter is a pointer
    word sum = 0;
    for (word i = 0; i < count; i += 1) sum += values[i];
    return sum;
}

total(table, 4);                // the name decays to &table[0]

a[i] is exactly *(a + i), so it works on any pointer — and there is no bounds checking anywhere.

Anything a list leaves out is zero, and C's rules hold: nested braces for nested aggregates, or none at all. A local's list may use run-time values; a global's must be numbers, or the addresses of strings, globals and functions, because it becomes bytes in the image.

Unions

union Word { word whole; byte halves[2]; };   // every member at offset 0

union Word w;
w.whole = 0xABCD;
w.halves[0]                     // 0xAB: the machine is big-endian

The one place Mona differs from C

struct Point points[3];

&points[0] + 1 == &points[1]    // true: adding moves whole elements
&points[1] - &points[0]         // 4 -- BYTES, not 1 element
Pointer subtraction yields bytes. Every other pointer operation behaves the way C taught you. This one does not, and it is worth reading twice before you rely on it.

The pointer-to-the-link idiom

Because & works on a member reached through a pointer, a list insert needs no special case for the head:

struct Node** link = &head;
while (*link != 0) {
    link = &(*link)->next;      // the address of the field that has to change
}
*link = fresh;

09 Talking to the hardware

The peripherals live in a port space separate from memory, unreachable by any pointer. Two builtins are the only way in, and each compiles to a single instruction. They are spelled with leading underscores — C's convention for names reserved to the implementation — so there is never a header to include and never a clash with a name of yours.

There are twenty-five builtins in all: these two, the three interrupt ones, the heap pair, six machine helpers — __vwrite, __vread, __vfill, __waitframe, __mulhi and __getkey — nine for memory, strings and math, and __ticks, __halt and __random, which are one instruction each. Seventeen of them become calls into small runtime routines, emitted only when a program actually uses one, so an unused builtin costs nothing at all.

__ticks, the only measurement the machine offers

TMRCOUNTER falls by one for every instruction the CPU executes, halted ones included, and it can be read. That makes an exact instruction count available to a program for the price of one IN.

__out(3, 30000);                // TMRPRELOAD: the counter only runs once it is set
word before = __ticks();
work();
word cost = before - __ticks(); // exactly how many instructions that took

It counts down, so the earlier reading is the larger one — and it is the timer's own counter, so it wraps at the preload rather than running freely.

__getkey, which drains the port for you

Returns (status << 8) | key, or 0 when nothing is waiting.

word k = __getkey();
if (k != 0) {
    word status = k >> 8;
    word key = k & 255;
    if ((status & 1) != 0) press(key);       // 1 is a key going down
}

KBDSTATUS is a bit field, not a flag, and reading KBDDATA is what clears it — so the only correct shape is collect first, decide afterwards. This is the one builtin that encodes a policy rather than exposing a primitive, and that is the point: it makes the trap below unskippable.

word value = __in(port);        // read a port
__out(port, value);             // write a port
portnamewhat it is
0IRQMASKone bit per device: keypad 1, timer 2, graphics 4
1IRQSTATUSwhich devices are asking
2IRQEOIwrite back what you handled
3TMRPRELOADinstructions between timer interrupts
4TMRCOUNTERhow many are left
5KBDSTATUSa key is waiting
6KBDDATAthe key; reading it lowers the request
7VIDMODE0 off, 1 text, 2 bitmap, 3 clear, 4 reset
8VIDADDRbyte address in video memory: y * 256 + x
9VIDDATAthe palette index to store there
10RNDGENread-only — a fresh random word every read
Writing a read-only port faults the CPU — ports 1, 4, 5, 6 and 10 — and so does naming a port above 10. The exception has nowhere to go: there is no vector for it, the CPU latches into fault mode, and everything after it throws. With a literal port the compiler rejects it outright; a computed one is never judged.
__out(7, 2);                    // VIDMODE 2: bitmap, 256 x 256, one byte a pixel
__out(7, 3);                    // VIDMODE 3: clear all 65,536 pixels in one instruction
__out(8, y * 256 + x);          // VIDADDR: where
__out(9, 255);                  // VIDDATA: what
Write the port as a literal in anything hot. OUT takes its port as an immediate or from a register and nothing else, so a port held in a variable has to be loaded into one first — and with every register busy the compiler frees one by pushing it. In cube.mona's inner loop that was three extra instructions per pixel.

The palette is arithmetic

It is a 3-3-2 RGB cube, so a colour is a formula rather than a lookup table: index = red * 32 + green * 4 + blue, red and green 0–7, blue 0–3. The channels are stepped by 36, 36 and 85, so pure red is (252, 0, 0) rather than (255, 0, 0) — index 255 is the one entry special-cased to true white. Drag these:

__mulhi, for the half of a product MUL throws away

MUL is 16 × 16 into 16 and the top half is simply gone. That is the machine's largest arithmetic hole, and the reason cube.mona works at a fixed-point scale of 128 rather than 256.

__mulhi(1000, 1000)             // 15, because 1000 * 1000 is 0x000F4240
1000 * 1000                     // 16960, which is 0x4240 -- the half MUL keeps

// fixed point at scale 256, both halves combined
word product = (__mulhi(a, b) << 8) | ((a * b) >> 8);

Recovering it takes four byte-wide multiplies and the carries between them — about thirty instructions, too many to inline and too fiddly to write twice. Two of those carries are invisible in a small test, so it is checked against exact arithmetic over 1,344 pairs.

Memory, strings and math

C's library staples, and the arithmetic this machine makes hard. Each one is checked against Java on the real simulator.

__memset(line, ' ', 16);          // a byte fill
__memcpy(&line[1], &line[0], 15); // overlap is safe, unlike C's
__strcpy(name, "mona");
__strlen(name)                    // 4
__strcmp("abc", "abd")            // -1: a sword, so < 0 means what it says
__sqrt(99)                        // 9, rounded down
__sin(64)                         // 256: 256 steps a turn, and 256 is 1.0
__cos(128)                        // -256
__fixmul(384, 512)                // 768: 1.5 * 2.0 at scale 256, signed
__random()                        // RNDGEN, one IN 10

__sin and __cos share one 65-word quarter-wave table, emitted once for either. __fixmul is (a * b) >> 8 on the whole 32-bit product, signed, which is what turning a point needs:

sword rx = __fixmul(x, __cos(a)) - __fixmul(y, __sin(a));
sword ry = __fixmul(x, __sin(a)) + __fixmul(y, __cos(a));

The text display is just memory

Thirty-two characters live at 0x1000, one byte each. No builtin, no driver — an ordinary array of bytes.

byte* screen = 4096;            // 0x1000
screen[0] = 'M';

10 The graphics card

The card has its own 64 KB, entirely separate from the machine's 4 KB and reachable only through VIDADDR and VIDDATA. What that memory means depends on the mode, and the two modes have almost nothing in common.

Bitmap — VIDMODE 2

All 65,536 bytes are the screen: 256 × 256, one byte per pixel, each byte a palette index. VIDADDR is y * 256 + x. No scrolling, no sprites, no memory to spare — and the palette is ROM, so it cannot be changed.

Tile — VIDMODE 1

The simulator calls this "text mode", which undersells it by a wide margin. It is a tile engine, and the 64 KB is laid out like one:

rangesizewhat lives there
0x0000–0x7FFF32 Ktile map — 128 × 128 cells, 2 bytes each: tile index, then colour index
0x8000–0x9FFF8 K256 tile definitions, 32 bytes each: 16 × 16 pixels, one bit per pixel
0xA000–0xA2FF768 Bpalette — 256 entries, 3 bytes of RGB each
0xA3011 Bbackground colour index
0xA302–0xA3032 BHScroll, in pixels
0xA304–0xA3052 BVScroll, in pixels
0xA306–0xA32532 Beight sprites, 4 bytes each: tile, colour, x, y
0xA326–0xFFFF23,754 Bfree — the card never reads it

Scrolling

The map is 128 tiles square, which is 2048 × 2048 pixels, seen through a 256-pixel window. The scroll registers are in pixels, not tiles, and clamp at 1792 — exactly 2048 − 256 — so the window slides to every corner of the map, one pixel at a time. The card draws 17 × 17 tiles to cover the partial ones at the edges.

Tiles are redefinable, and start as a character set

All 256 definitions are loaded from ROM at reset with a font, which is why writing a letter's code into the map prints that letter. They are ordinary memory: overwrite one and it is your shape from then on. A definition is 32 bytes — 16 rows of 16 bits, MSB first. A set bit takes the cell's colour index; a clear bit shows the background colour. Two colours per cell, out of 256.

Redefining tile 0 paints the entire map. Every cell a program has not written is (tile 0, colour 0), so a solid tile 0 covers all 2048 × 2048 pixels in palette entry 0 and the background colour stops showing anywhere.

Sprites

Eight of them, 16 × 16, drawn from the same tile definitions in a single colour, always over the map. Their clear bits are transparent rather than background — which is the one thing a tile cannot do. They live in screen space, so scrolling the map does not move them, and x and y are single bytes, so a sprite near an edge is clipped rather than wrapped. Tile index 0 means off, so zeroing that byte hides a sprite.

A frame clock, for free

Whenever the display is on, the card raises interrupt line 2 — IRQMASK bit value 4 — every 20 ms. That is a genuine 50 Hz wall-clock tick, and it is the only one the machine has: TMRPRELOAD counts instructions, so its rate moves with the simulator's speed setting while this does not.

void defineTile(word which, word row) {         // 32 bytes: sixteen 2-byte writes
    word at = 32768 + which * 32;               // 0x8000 + 32 * which
    word end = at + 32;
    while (at < end) {
        __out(8, at);
        __out(9, row);                          // in tile mode VIDDATA stores TWO bytes
        at += 2;
    }
}

void setCell(word x, word y, word tile, word colour) {
    __out(8, (y * 128 + x) * 2);
    __out(9, tile * 256 + colour);              // one cell, one write
}

word main() {
    __out(7, 1);                                // tile mode
    defineTile(1, 65535);                       // 0xFFFF: a solid block
    setCell(0, 0, 1, 224);                      // draw it in red
    __out(8, 41728); __out(9, 3);               // 0xA301: background = blue

    __out(8, 41734); __out(9, 1 * 256 + 28);    // 0xA306: sprite 1 = tile 1, green
    __out(8, 41736); __out(9, 100 * 256 + 50);  // 0xA308: at x=100, y=50

    __out(8, 41730); __out(9, 8);               // 0xA302: scroll right 8 pixels
    return 0;
}

Moving blocks in and out: __vwrite, __vread, __vfill

There is no DMA on this machine — ports 0 to 10 are all of it — so every byte crosses through VIDADDR/VIDDATA one write at a time. That loop is not the same in both modes, since a VIDDATA write moves two bytes in tile mode and one in bitmap. These three read VIDMODE and branch, so a byte count means a byte count either way.

__vwrite(vaddr, from, count);   // RAM -> video memory, count bytes
__vread (vaddr, into, count);   // video memory -> RAM
__vfill (vaddr, value, count);  // a 16-bit pattern, count bytes

RAM is big-endian and VIDDATA splits a word the same way round, so in tile mode a word passes through untouched, no shuffling. An odd count ends on a lone byte that cannot be written by itself, so the tail reads the pair back, replaces one half and writes it again: the byte after the range is left as it was.

tile modebitmap mode
__vwrite4.5 instructions / byte10
__vread4.59
__vfill4.08
the same loop written in Mona1416

Tile mode is cheaper per byte because one VIDDATA write moves two of them. The gap against hand-written code is not cleverness — the helper keeps the address and the pointer in B and C and ends on a precomputed limit, which a Mona loop cannot do because it has locals to spill.

__vfill's pattern is a whole cell in tile mode — high byte the tile, low byte the colour — and just a palette index in bitmap mode:

__vfill(0, 0, 2048);            // clear the top-left of the tile map
__vfill(0, 0x0503, 512);        // or fill it with tile 5 in colour 3

Build it in RAM, push it across, take the RAM back

The card's memory is the one place a 4 KB machine has room to spare, and the flow is always those three steps. The heap is the natural place to build it, precisely because you want the space returned.

word main() {
    __out(7, 1);                            // tile mode

    // 32 definitions -- a whole kilobyte of shapes -- in a buffer that only has to
    // exist for as long as it takes to push it across.
    byte* shapes = __alloc(32 * 32);
    if (shapes == 0) return 1;
    for (word i = 0; i < 32 * 32; i += 1) {
        shapes[i] = generate(i);
    }

    __vwrite(32768, shapes, 32 * 32);       // 0x8000: into the card
    __free(shapes);                         // and the kilobyte is yours again

    // The shapes live in video memory from here. The program keeps none of them.
    ...
}

A kilobyte is a quarter of everything this machine has, so handing it back is not a nicety. The same shape of code loads a palette (0xA000, 768 bytes), a sprite table (0xA306, 32 bytes) or a screenful of map — and in reverse, it turns the 23,754 free bytes above 0xA326 into swap space.

Push once during setup, not per frame. Every byte still goes through a port, so a kilobyte is a few thousand instructions. There is no transfer engine to do it for you.

Frame pacing: __waitframe

Blocks until the card's next refresh, fifty times a second, by polling IRQSTATUS — so it needs no handler, no __setisr and no __sti. Frame pacing is available to a program that wants nothing else to do with interrupts.

word main() {
    __out(7, 1);
    while (1) {
        __waitframe();          // 20 ms of wall time, every time
        // ... move something, draw it ...
    }
}

If the display is off it returns immediately, since there would be no refresh to wait for and the wait would never end.

Reading video memory, and 23 KB of scratch

Writing VIDADDR pre-loads VIDDATA from that address, so video memory can be read as well as written — two instructions a time.

word peek(word at) {
    __out(8, at);
    return __in(9);                 // in tile mode a big-endian word; in bitmap, a byte
}

In tile mode the card never looks above 0xA326, which leaves 23,754 bytes it will not touch — five and a half times the machine's entire RAM, usable as slow but real storage.

The differences that catch people

  • A VIDDATA write stores two bytes in tile mode (the high byte at VIDADDR, the low at VIDADDR + 1) and one in bitmap mode. Two bytes is exactly one map cell, or half a sprite record.
  • The palette is programmable in tile mode only. Bitmap mode reads the ROM and ignores 0xA000 entirely.
  • VIDMODE 3 clears all 64 KB in bitmap mode, but only the 32 KB map in tile mode — definitions, palette, scroll and sprites all survive. VIDMODE 4 resets everything and reloads the tile ROM.
  • VIDADDR does not auto-increment. Four instructions per pixel is the floor in bitmap mode, and two writes per cell in tile mode.
All of the above is a test, not a reading of the source. TileModeIT drives the real card from Mona and asserts on the pixels it renders — the scroll offset, the redefined shapes, sprite transparency, the palette, and what survives a clear.

Pixels, colours and a filled box

The bitmap palette is a fixed 3-3-2 colour cube, so a colour is arithmetic. A rectangle is one __vfill per row, which is far cheaper than plotting it pixel by pixel.

enum Port { VIDMODE = 7, VIDADDR = 8, VIDDATA = 9 };
enum Mode { MODE_TILE = 1, MODE_BITMAP = 2, MODE_CLEAR = 3 };

// The palette is a 3-3-2 cube: red and green 0..7, blue 0..3.
word rgb(word r, word g, word b) {
    return r * 32 + g * 4 + b;
}

void plot(word x, word y, word colour) {
    __out(VIDADDR, y * 256 + x);
    __out(VIDDATA, colour);
}

// One __vfill a row: in bitmap mode every byte takes the pattern's low half.
void rect(word x, word y, word w, word h, word colour) {
    for (word row = y; row < y + h; row++) {
        __vfill(row * 256 + x, colour, w);
    }
}

word main() {
    __out(VIDMODE, MODE_BITMAP);
    __out(VIDMODE, MODE_CLEAR);
    rect(40, 40, 64, 32, rgb(7, 4, 0));     // an orange box
    plot(128, 128, rgb(7, 7, 3));           // one white pixel
    return 0;
}

Text, a tile of your own, and the palette

In tile mode every cell shows one of 256 shapes, and the ROM starts them as a character set — so writing a letter's code into a cell prints it. Any shape can be replaced with __vwrite, and so can any palette entry. Build the data as const arrays: they sit in the image, and nothing runs to make them.

enum Port { VIDMODE = 7, VIDADDR = 8, VIDDATA = 9 };
enum { MODE_TILE = 1, HEART = 1, PINK = 200 };

const word TILES   = 0x8000;    // 256 definitions, 32 bytes each
const word PALETTE = 0xA000;    // 256 entries, 3 bytes each: red, green, blue

// Sixteen rows of sixteen pixels, two bytes a row, leftmost pixel in the top bit.
const byte heart[32] = {
    0x00, 0x00, 0x1C, 0x38, 0x3E, 0x7C, 0x7F, 0xFE, 0x7F, 0xFE, 0x7F, 0xFE, 0x3F, 0xFC, 0x1F, 0xF8,
    0x0F, 0xF0, 0x07, 0xE0, 0x03, 0xC0, 0x01, 0x80, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00,
};
const byte pink[3] = {255, 105, 180};

// A cell is two bytes: the tile, then the colour. Row 0, column 0 is at 0.
void putText(word column, word row, const byte* text, word colour) {
    word at = (row * 128 + column) * 2;
    while (*text != 0) {
        __out(VIDADDR, at);
        __out(VIDDATA, *text++ * 256 + colour);
        at += 2;
    }
}

word main() {
    __out(VIDMODE, MODE_TILE);
    __vwrite(TILES + HEART * 32, heart, 32);        // tile 1 is a heart from now on
    __vwrite(PALETTE + PINK * 3, pink, 3);          // colour 200 is pink

    __out(VIDADDR, 0xA300);                         // the background colour is the
    __out(VIDDATA, 3);                              // low byte of this pair: blue

    putText(1, 1, "I LOVE MONA", 15);
    __out(VIDADDR, (1 * 128 + 13) * 2);
    __out(VIDDATA, HEART * 256 + PINK);             // and a heart after it
    return 0;
}

A sprite that moves over a map that scrolls

A sprite is a four-byte record, and a struct with those four bytes in that order is exactly its layout — Mona adds no padding — so it can be sent across whole. __waitframe paces the loop in real time, and __getkey reads the keypad without any interrupt handler.

enum Port { VIDMODE = 7, VIDADDR = 8, VIDDATA = 9 };
enum { MODE_TILE = 1, KEY_DOWN = 1 };

const word SPRITES = 0xA306;    // eight records of four bytes
const word HSCROLL = 0xA302;    // the window's offset, in pixels

// The card's own record layout, so a struct goes across as it stands.
struct Sprite {
    byte tile;
    byte colour;
    byte x;
    byte y;
};

struct Sprite player = {'@', 28, 120, 120};

void show(word n, struct Sprite* s) {
    __vwrite(SPRITES + n * 4, s, 4);
}

word main() {
    __out(VIDMODE, MODE_TILE);
    show(0, &player);

    word scroll = 0;
    while (1) {
        __waitframe();                              // 50 times a second
        word k = __getkey();
        if (k != 0 && ((k >> 8) & KEY_DOWN) != 0) {
            word key = k & 255;
            if (key == 'a' && player.x > 4) player.x -= 4;
            if (key == 'd' && player.x < 236) player.x += 4;
            show(0, &player);
        }
        __out(VIDADDR, HSCROLL);                    // drift the map under the sprite
        __out(VIDDATA, scroll);
        if (++scroll > 1792) scroll = 0;            // the scroll registers stop at 1792
    }
    return 0;
}

Habits that keep it fast

  • Set up once, change little. Shapes, palette and the first picture go across at the start; after that, touch only what moved. ivona.mona never clears the screen after its first frame, and erases a letter by drawing it again in colour 0.
  • A pixel costs four instructions — two writes, each needing the value in A — and nothing makes it cheaper, because VIDADDR never advances. Carry the address rather than recomputing y * 256 + x, as cube.mona's line drawer does.
  • Tile mode draws 256 pixels a write. For anything built of blocks, a map cell is far cheaper than pixels — blocks.mona draws a whole landscape from four ROM shapes, with no shapes uploaded at all.
  • Let the card remember. The map can be read back, so a game can ask the card what is on a square instead of keeping its own copy — snake.mona detects collisions that way.

12 The heap

struct Node* node = __alloc(sizeof(struct Node));
if (node == 0) return 1;        // always check: the machine has 4 KB
node->key = 7;
__free(node);                   // freeing 0 is allowed, and does nothing

A program that calls __alloc gets a heap; one that does not, does not. Nothing has to be enabled — a forgotten flag would be a failure that teaches nothing, so the compiler reads the need off the source. It reads the shape off the source too, and picks one of three allocators accordingly:

tierchosen whencost
bumpthe program never frees8 instructions, no bookkeeping at all
slabevery allocation is the same constant sizeone bit per cell, plus a hint
bitmapanything elsegeneral, still headerless

__free checks what it is handed. A pointer that is outside the heap, misaligned, not the start of a block, or already freed never came from __alloc — so rather than quietly corrupting the heap it prints HEAP CORRUPT and halts.

Neither is re-entrant. If an interrupt handler allocates and the program does too, both can be handed the same memory: each reads a word, decides from it, and writes it back. The compiler warns when it can see both. The fix is __cli() / __sti() around the program's own allocations.
Write sizeof, not the number. __alloc(6) works today and keeps working — silently and wrongly — the moment someone adds a member.
Reach for it last. A fixed array is usually the better tool on a 4 KB machine: the compiler reports its size before the program runs, there is no allocator in the image, and nothing can run out halfway through. The heap earns its place when a program genuinely cannot know how much it will need. tree.mona builds a search tree from a pool of nodes; heap.mona is the one example that allocates.

13 Interrupts

One vector, at 0x0003, shared by every device — so a program has exactly one handler and works out who called by reading IRQSTATUS. The address is stored at run time, so handlers can be swapped.

word ticks = 0;

void onIrq() {
    word pending = __in(1);         // IRQSTATUS: who asked
    if (pending & 2) {              // bit 1: the timer
        ticks = ticks + 1;
    }
    __out(2, pending);              // IRQEOI: acknowledge, or IRET returns
}                                   // straight back into the same request

word main() {
    __setisr(&onIrq);               // install it
    __out(0, 2);                    // IRQMASK: the timer only
    __out(3, 1000);                 // TMRPRELOAD: every 1001 instructions
    __sti();                        // and let interrupts through
    while (1) { }
}

Delivery needs both the device's bit in IRQMASK and the global enable from __sti(). A handler cannot interrupt itself: entering one clears the global enable and IRET restores it. Keep it short — everything it does happens while the program is stopped.

Read KBDDATA before you acknowledge

The keypad is the only level-triggered device here. A keypress raises both the controller's level bit and its status bit; reading KBDDATA lowers the level and only the level, and IRQEOI clears the status bit — except that IRQEOI is status ^= value followed by status |= level, so it restores whatever the level still asserts. Both steps are needed, in that order.

what the handler doeswhat happens
reads KBDDATA, then IRQEOIcorrect — one keypress, one entry
IRQEOI, then reads KBDDATAthe level was still high, so the status bit comes straight back and the handler runs twice for one press. Nothing hangs; a counter is just doubled
IRQEOI, never reads KBDDATAthe level never falls, so every acknowledgement re-raises the request and the program stops making progress
The middle one is what bites, because it does not look like an interrupt bug — it looks like a game reacting twice to one key. And since IRQEOI is an XOR, acknowledging a line that is not raised sets it: write back what you read from IRQSTATUS, never a constant you assumed.
The timer counts instructions, not time, because every instruction here is one clock tick. A second is however many instructions the simulator runs per second, which is the speed in its Speed menu: with the preload at 1000, ticks per second is the speed in kHz.

14 Where everything lives

4,128 bytes altogether: 4,096 of RAM, then the 32-byte text display. Inside the RAM, three things share one space with nothing between them.

0x0000image code, then globals, strings, jump tables
heap if the program allocates — grows up ↓
free whatever is left over
0x0FFFstack grows down ↑
0x1000text display 32 bytes, memory mapped
Nothing detects a collision. A stack that grows into the code overwrites it, and the machine's first complaint is Invalid opcode at some unrelated address — long after the evidence is gone. That is why the compiler computes the stack requirement up front where it can, and checks at run time where it cannot.

15 Things that bite

Every one of these has actually cost someone time.

  • MUL is 16 × 16 into 16 bits. The top half is gone, with no warning: 1000 * 1000 is 16960. cube.mona uses a fixed-point scale of 128 rather than 256 for exactly this reason.
  • There is no MOD instruction. a % b becomes a - (a / b) * b — three instructions, not one.
  • Pointer subtraction is in bytes. The one deliberate departure from C.
  • Nothing clips and nothing is bounds checked. A screen coordinate that leaves 0…255 does not fault; it wraps into video memory and draws somewhere else entirely.
  • Structs are packed, so sizeof will not agree with a C compiler's.
  • A big function may not compile at -O0. An indirect operand's displacement is a signed byte, so a frame reaches 64 slots — and unoptimized, every intermediate takes one.
  • 4,096 bytes is everything. --stats reports what a program costs, and the compiler refuses one that does not fit rather than emitting it.

16 Using monac

monac takes one source file and writes one assembly file. Options may come before or after the file name.

monac <input.mona> [options]

Without -o, the output goes next to the input with its extension changed — games/snake.mona becomes games/snake.asm. Messages and --stats go to standard error, so they never end up inside the assembly.

What --stats tells you

$ monac cube.mona --stats

  • instructions — every line of the image, data directives included, so a table in an initializer list counts once per entry. A measure of size. Speed is how many instructions run, which depends on the input and the loops.
  • stack at most — the deepest the stack can go, from the call graph. A recursive program has no such bound: it reports unbounded (recursive), and the compiler adds a check that stops the program with STACK OVERFLOW on the display instead of letting it overwrite itself.
  • bytes free — what is left once the image and the stack are counted. A heap, if the program has one, lives there.

Every message names the file, the line and the column, says whether it is an error (no output) or a warning (output, but look), and shows the line with the spot underlined. Some add a note saying why, or what to do.

18 Running and debugging

The simulator shows every register and every byte of memory, and can run one instruction at a time. The compiler's job is to make the assembly readable enough that this is useful.

Reading the output

This is all of simple.mona at -O1:

m_add:
        ADD   B, [SP+3]
        MOV   A, B
.L0_epi_add:
        RET

m_main:
        PUSH  20                            ; arg 1
        MOV   B, 10
        CALL  m_add
        ADD   SP, 2                         ; reclaim arguments
.L1_epi_main:
        RET
you seeit is
m_addthe function add. Every function is m_ and its name
g_scorethe global score
.L4_then, .L7_endifthe branches of an if, a loop's head and exit, and so on — numbered, and named after what they belong to
.L0_epi_addthe end of add, where every return goes
[SP+3]a value in the stack frame, counted in bytes up from the stack pointer

And the calling convention, which is visible above: the first argument travels in B, the rest are pushed, and the result comes back in A. So add finds a in B and b on the stack, three bytes up — above the return address CALL pushed. No register survives a call, and the caller takes its arguments back off the stack afterwards. When main returns, the startup code halts the machine with main's result still in A.

Registers

registerwhat the compiler uses it for
Ascratch, the only register OUT, MUL and DIV use, and the return value
B, Clocal variables, handed out by the register allocator; B also carries the first argument
Da frame pointer in the hand-written runtime helpers; compiled functions address their frame from SP instead

Techniques that work

  • Slow it down. At the simulator's default of 4 Hz you can watch each instruction execute and the registers change. The labels above tell you where you are in the source.
  • Stop where you want to look. __halt() stops the machine on the spot, with every register and byte left as it was.
  • Print to the display. The text display is 32 bytes of memory at 0x1000, so writing SCREEN[0] = '0' + x % 10 is a one-line trace.
  • Return it. Whatever main returns is in A when the machine halts.
  • Compare levels. Compile with -O0: the code is longer but every variable lives at a fixed place in the frame, which is easier to watch in the memory view.

19 Writing fast Mona

On this machine every instruction takes exactly one clock tick, so a program's running time is simply the number of instructions it executes. There are no caches or pipelines to reason about — which makes it unusually easy to know what is fast. The rules below are the ones the examples follow, and each one comes from measuring them.

  1. Name constants with enum or const, never a plain variable. Both are constants, so __out(VIDADDR, x) is OUT 8 and i < LETTERS compares with an immediate. OUT takes nothing but an immediate or a register, so a port in an ordinary global costs a load every time — and in a tight loop, with every register busy, a push and a pop as well. 
    enum Port { VIDMODE = 7, VIDADDR = 8, VIDDATA = 9 };
const word WIDTH = 256;
byte* const SCREEN = 4096;          // a const pointer with a constant address folds too
  2. Write tables as initializer lists. A global's list is data in the image. Filling the same table with assignments at startup costs the code to do it as well as the table. 
    const sword quarter[17] = {0, 13, 25, 37, 49, 60, 71, 81, 91, 99, 106, 113, 118, 123, 126, 127, 128};
  3. Prefer fixed arrays to the heap. If the program knows how much it needs, declare it: no allocator in the image, no bookkeeping, nothing that can fail at run time, and --stats shows the cost up front. tree.mona takes its nodes from a pool.
  4. Keep word and unsigned where you can. The machine has no sign flag, so a signed comparison costs extra instructions on each side, and signed / and % go through a helper routine. If a value cannot be negative, do not declare it signed.
  5. Mind the loop, not the program. Only the innermost loops matter. A call inside one costs the pushes, the CALL, the RET and the clean-up, every time round — for a two-line helper, spell it out. cube.mona's drawing loop was 34 instructions a pixel before its helper was spelled out and its address carried (the next rule); it is about 18 now.
  6. Carry a value instead of recomputing it. y * 256 + x every pixel is three instructions; adding 1 or 256 to an address you already have is one.
  7. Two values fit in registers. B and C are all the allocator has. The rest live in the frame — and reading one there is free, since the ALU takes a memory operand at no extra cost, but writing one is an extra store. A loop that updates two values is cheaper than one that updates three.
  8. Divide by powers of two, unsigned. For a word, the compiler turns i % 128 into i & 127 and i / 8 into a shift — one instruction each. For an sword, which has to round toward zero, the same % 128 is a call to a helper routine. A ring buffer whose length is a power of two wraps with an AND.
  9. Write out what is short and known. When every value is a constant, straight-line code folds to one MOV and one OUT per write — smaller and faster than a loop, which pays for its counter and its loads, or a helper, which pays for its calls. graphics.mona writes four tiles in 25 instructions that way; the loop was 40, and ran more than four times as many.
  10. Read what you wrote. --dump-asm and a count of the instructions inside your hottest loop settle any argument about which version is faster.

22 What is not here

typedef, designated initializers, variadic functions, a preprocessor, separate compilation, floating point.

None of those is coming, and roadmap.md says why for each. For typedef and the preprocessor: every type starting with a keyword is what lets (byte)x and (x) be told apart without a symbol table.

Floating point is absent because the machine has none. Fixed point is the answer, and cube.mona — a rotating 3D cube in 1,480 bytes — is what it looks like.
